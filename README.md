## 1. 这个 skill 能做什么

huawei-mathmodel 将数学建模工作组织为可以分次执行、可以续接、可以核对完成依据的流程。它从题意和数据出发，逐步形成数学模型、求解实现、实验结果与 Markdown 论文。

它适合以下使用方式：

- 拿到多道赛题，先比较可解性、数据支持和实现风险，再选题。
- 已经选定题目，只需要拆题、检查数据和设计建模方案。
- 已有方案，分批完成基线、主方案、对照实验和必要验证。
- 代码在自己的电脑或服务器运行，把日志与结果交回后继续分析。
- 全部实验完成后，根据真实结果撰写 Markdown 论文。
- 接手已有项目，检查漏答、公式与代码不一致、数值引用错误和失效证据。

### 1.1 主要能力

| 能力 | 实际作用 |
| --- | --- |
| 分阶段推进 | 可指定一个阶段、几个阶段、一问或几个任务，完成本轮范围后停止 |
| 清晰规划 | 用 plan.md 说明总体路线、阶段安排、预算、风险和决策 |
| 具体待办 | 用 todo.md 展示任务、依赖、状态、完成标准和证据 |
| 动态拆题 | 按真实题面提取所有问题及子要求，不限定三问 |
| 有依据的建模 | 交代变量、单位、假设、目标、约束、求解方法及验证方法 |
| 实际运行记录 | 区分代码已写、运行成功、结果有效和结论得到支持 |
| 数值追溯 | 将论文关键数字绑定到实验、结果文件、指标位置、单位和场景 |
| 变更后复核 | 输入或代码改变后识别失效证据，由执行者标记并重验受影响任务 |
| 论文级绘图 | 真实数据生成实验图，统一视觉与统计表达；框架/流程图默认给 GPT Image 提示词包 |
| Markdown 交付 | 最终论文为 paper/paper.md，图表采用可追溯数据与相对路径 |

### 1.2 使用边界

skill 提供工作规则、参考指南和辅助脚本；实际读文件、检索资料、执行模型或操作服务器，取决于当前环境的能力与已有授权。辅助脚本负责记录和一致性检查，不会代替模型运行，也不是后台自动调度系统。

脚本通过不能独立证明数学正确性、模型适用性或文献真实性，这些内容有单独的审查步骤。训练中的完整 Markdown 成果也不代表已经符合某届比赛上传格式或完成官方提交。正式比赛需核对当届规则、答疑及 AI 使用要求，并保存真实使用记录。

本工作流参考了 [MathModelAgent](https://github.com/jihe520/MathModelAgent) 的阶段组织与成果交接思路，结合本项目的 Markdown 交付、明确停止点和证据管理要求编写。本文描述的能力以当前 huawei-mathmodel 文件和脚本为准。

## 2. 快速开始与指令写法

### 2.1 如何调用

在已安装且能够使用该 skill 的会话中，可以直接写“使用华为杯数学建模工作流”，也可以在指令中包含 $huawei-mathmodel。

先上传题面及附件，或者说明当前环境可以访问的项目目录。只提供一个不可访问的本地路径，不能视为已经提供了材料。

### 2.2 首次使用：先做规划与分析

下面这条指令适合“最终要完成整题，但这一轮先设计方案”的情况。

~~~text
使用 $huawei-mathmodel 处理我提供的题目和附件。

项目最终目标：完成整题和 Markdown 论文。
本轮范围：只执行 S0—S3，完成方案设计后停止。

请完成：
1. 清点题面与附件，记录缺失材料和关键未知项。
2. 逐项拆解所有问题、子要求和问题之间的依赖。
3. 检查数据结构、单位、缺失值、异常值及适用条件。
4. 为每问提出有依据的基线、主方案和必要备选。
5. 设计验证、对照、实验预算和停止条件。
6. 建立清晰的 plan.md、todo.md、state.json 及分析报告。

本轮可以做必要的数据检查，不运行正式求解或模型比较实验。
不生成论文正文、摘要或占位稿。
不要把分析完成标成实际求解完成。
最后汇报已完成内容、阻塞项、下一阶段任务和对应产出。
~~~

### 2.3 最小调用：只启动项目

~~~text
使用 $huawei-mathmodel。这次只执行 S0。
先读取我提供的材料，建立项目计划与待办，确认范围、资源和缺口。
完成接收报告与计划后停止；选题分析、模型实现和论文留到后续阶段。
~~~

### 2.4 一条清晰指令包含哪些信息

| 信息 | 建议写法 |
| --- | --- |
| 项目位置 | “使用我刚上传的题面和附件”或“续接当前可访问的项目目录” |
| 本轮范围 | “只做 S2”“完成 S4—S5”“只执行问题二的基线任务” |
| 输入与已有状态 | “S3 已完成，请先核对已有方案和证据” |
| 约束 | “本轮只用 CPU”“沿用已锁定划分”“不修改原始数据” |
| 产出 | “输出数据检查报告、派生数据说明和更新后的 todo” |
| 完成标准 | “逐项检查字段、单位、异常及下游影响” |
| 停止点 | “完成当前阶段后停止，不进入下一阶段” |

预算未知可以明确写未知；不要为了补齐指令编造截止时间、计算资源或已完成状态。

## 3. 分阶段执行与续接规则

### 3.1 四个概念需要分清

| 概念 | 含义 | 示例 |
| --- | --- | --- |
| 项目总范围 | 最终打算完成哪些工作，由 scope 表示 | 最终完成整题与论文，scope=full |
| 本轮执行范围 | 这次对话实际处理什么 | 只执行 S2—S3 |
| 题目要求 | 题面要求回答的内容 | Q2.a 为预测，Q2.b 为解释影响因素 |
| 执行任务 | 达成要求所需的具体动作 | 检查时间划分、训练基线、计算误差 |

scope=full 不表示本轮必须直接做到论文交付。一个完整项目可以分十轮或更多轮完成，也可以把同一阶段拆成多个小任务。

### 3.2 默认行为

1. 用户给出明确阶段或任务集合时，只执行该范围。
2. 没有给出范围时，默认处理当前未完成阶段；新项目从 S0 开始。
3. 同一轮已经指定多个阶段时，可在范围内连续推进，无需每个阶段重复确认。
4. 达到停止点后，更新记录、交付阶段成果并结束。
5. 只有明确要求连续完成全流程时，才持续推进到完整交付；阶段检查仍需完成。

### 3.3 “继续”具体表示什么

- 当前阶段还未完成：继续处理该阶段的未完成任务。
- 当前阶段已经通过：进入下一个依赖满足的阶段，完成后停止。
- 当前阶段受阻：先报告实际缺口，继续同一范围内不受影响的工作。
- 已有结果有效：读取并复用，不默认重跑。
- 发现数据或代码变化：先评估影响，标记失效项，再安排必要重验。

如果希望精确控制，直接指定阶段或任务 ID，比只说“继续”更清楚。

### 3.4 能否直接从中间阶段开始

可以。例如已有模型方案时，直接要求执行 S4；已有全部实验结果时，直接要求核验后执行 S6。

执行者仍需读取必要上游材料。缺少关键输入、建模依据或实验记录时，会列出缺口和最小补齐任务；不能凭“前面应该完成了”直接把后续阶段判为通过。

### 3.5 本轮执行约定如何保存

在 plan.md 开头记录本轮阶段、题号或任务 ID、输入依据、交付物、通过标准、停止点及论文是否开放。todo 保留整个项目已知任务，在备注中区分本轮执行和后续任务。

todo 中“下一步”列出的任务表示依赖已满足；实际执行还要服从本轮范围。该列表不是要求一次执行全部待办的自动队列。

## 4. 开始前需要提供的材料

| 材料 | 建议内容 | 缺失时如何处理 |
| --- | --- | --- |
| 完整题面 | 所有问题、图示、公式、附件说明及补充要求 | 不能声称已经完整拆题 |
| 数据附件 | 原始表格、图片、代码、字典或说明文件 | 记录具体阻塞要求，先做可行的分析 |
| 比赛或训练状态 | 正式比赛、往届题训练、自拟练习或未知 | 记录 unknown，不自行认定为训练 |
| 官方要求 | 当届规则、更正、AI 使用说明 | 正式比赛中核实有效来源 |
| 截止时间 | 日期、时区、可用工作时间 | 保留未知，先建立相对预算 |
| 计算资源 | 语言、CPU/GPU、内存、软件、运行限制 | 不假设有 GPU 或商业求解器 |
| 已有工作 | 计划、代码、数据处理、结果、日志、报告 | 核对真实文件后决定复用范围 |
| 本轮目标 | 阶段、题号、任务、预期产出及停止点 | 默认从当前未完成阶段开始 |

建议上传原始题面，同时保留原始数据。派生数据、修正记录和最终结果应能追溯到输入；不要只提供一张无法核验计算过程的结果截图。

## 5. 九阶段流程与通过条件

S 表示工作阶段；G 表示对应的阶段检查。例如，S4 是基础实现工作，G4 是对该工作的检查结论。

| 阶段 | 主要输入 | 核心工作 | 主要产出 | 通过条件 |
| --- | --- | --- | --- | --- |
| S0 接收与规划 | 用户目标、题面、材料与资源约束 | 清点材料、确定总范围和本轮边界、安排预算 | plan.md、todo.md、state.json、reports/intake.md | G0：范围与关键输入已核实，缺口和预算已记录 |
| S1 选题与拆解 | 题面、候选题、队伍条件 | 必要时选题；提取全部问题与子要求；梳理依赖 | reports/requirements.md、要求清单 | G1：全部要求有原文出处与覆盖安排 |
| S2 数据与假设检查 | 原始数据、题设、字段说明 | 核对结构、单位、缺失、异常、划分、歧义与假设 | reports/data_assumptions.md、派生数据及处理记录 | G2：数据或条件含义清楚，关键问题已处理或明确条件化 |
| S3 建模与验证设计 | 拆题结果、可用数据、假设 | 形式化模型、选择方法、设计验证、约定接口和预算 | reports/modeling.md | G3：方案回答题意、可以实现、可以评价 |
| S4 基础实现 | 已核实的方案、数据和环境 | 小实例检查、实现求解、运行基线、独立核对关键约束 | code/、results/、reports/baseline_check.md | G4：基础路径实际跑通，必要边界与正确性检查通过 |
| S5 改进与验证 | 基线、误差分析、实验计划 | 执行有依据的改进、公平对照及必要稳健性等分析 | reports/results.md、完整实验记录、真实图表 | G5：主要结论有相应证据，局限与负面结果如实记录 |
| S6 Markdown 论文 | 全部有效实验或推导结果、核验记录 | 组织逐问论证、公式、结果、图表、引用与摘要 | paper/paper.md、figures/ | G6：答题完整，数字与依据一致，文稿可读 |
| S7 最终验收 | 题面、模型、代码、结果、论文 | 分别检查题意、数学、实现与表达；核对证据版本 | reports/review.md、reports/audit.json | G7：必要检查通过，无未处理的硬错误和漏答 |
| S8 交付归档 | 已验收成果、支持文件、交付范围 | 整理使用说明、最终状态与版本快照 | reports/delivery.md、delivery_manifest.json | G8：交付材料齐全，版本与状态明确 |

### 5.1 阶段不是一次性的直线

问题来源决定回退位置：

| 发现的问题 | 主要回退位置 | 后续受影响内容 |
| --- | --- | --- |
| 漏读题意或约束 | S1 | 模型、任务清单、求解与答题覆盖 |
| 单位错误、数据含义错误、划分泄漏 | S2 | 数据处理、实验及相关结论 |
| 目标函数、假设或模型结构不成立 | S3 | 求解实现、验证方案与结果 |
| 代码实现、求解状态或约束检查错误 | S4 | 实验结果、图表和引用 |
| 对照不公平、结果不稳定、证据不足 | S5 | 最终方法选择与结论强度 |
| 已核实结果在论文中写错或漏写 | S6 | 正文、摘要、表格、图片或引用 |

重新运行只针对受影响范围；仍然有效的上游资料与实验可以保留。

### 5.2 一个阶段如何分多轮完成

S4 可以拆成“问题一基线”“问题二基线”“联调与约束复核”。S5 可以拆成“主方案比较”“敏感性分析”“实验汇总与结论检查”。

只完成其中一部分时，对应任务可以 DONE，整个阶段的必要任务仍未全部完成，阶段检查不能提前 PASS。

## 6. plan、todo 与状态管理

### 6.1 三份文件的职责

| 文件 | 负责回答的问题 | 更新方式 |
| --- | --- | --- |
| plan.md | 为什么采用这条路线？本轮到哪里停止？如何安排时间和风险？ | 根据实际决策维护 |
| state.json | 哪些要求、任务、检查和实验是什么状态？证据在哪里？ | 根据真实工作更新结构化记录 |
| todo.md | 现在具体做哪些任务？哪些可执行、受阻或已完成？ | 更新 state.json 后通过 sync 生成 |

不要只在 todo.md 中手动打勾而不更新 state.json。下一次 sync 会依据结构化记录重新生成待办。

### 6.2 plan.md 应包含的内容

1. 项目总目标、比赛或训练状态、最终交付形式。
2. 本轮阶段、题号或任务范围、停止点与本轮交付。
3. 当前已核实成果、尚未验证内容及证据位置。
4. 题面、附件、官方规则、更正与原文出处。
5. 各问题的依赖关系、关键瓶颈、基线、主方案与备选。
6. 阶段输入、工作、产出、通过标准、预算与失败回退。
7. 时间里程碑、计算资源、单次运行预算与停止条件。
8. 实验协议：主指标、对照条件、划分、参数选择与随机性处理。
9. 决策与变更记录：原因、影响范围、需要重验的结论。
10. 阻塞项、恢复条件、可继续任务与建议下一步。

下面是“本轮执行约定”的写法示意，不是论文模板：

~~~markdown
## 本轮执行约定

- 项目总范围：整题求解与 Markdown 交付。
- 本轮阶段：S4。
- 本轮任务：问题二基线实现、运行与原始约束复核。
- 上游依据：先核对 requirements、modeling 和数据处理报告。
- 预期产出：代码、结果文件、真实运行日志、基础检查报告。
- 完成标准：代码实际执行，输入输出可追溯，必要约束复核通过。
- 停止点：完成本轮任务和记录后停止，不进入 S5 或 S6。
- 论文状态：尚未开放写作。
- 预算：按当前已确认资源填写；未知项保留未知。
~~~

### 6.3 todo 的任务粒度

任务要小到能够判断“做了什么、是否通过、证据是什么”。

| 不够明确的任务 | 更清楚的写法 |
| --- | --- |
| 完成第二问 | 实现第二问基线，保存解和求解状态，并独立回代容量与整数约束 |
| 优化模型 | 针对已发现的误差来源比较候选修改，在同一评价协议下报告变化 |
| 检查数据 | 检查主键重复、时间连续性、单位和缺失模式，记录各自下游影响 |
| 写好论文 | 在写作前提满足后，完成第二问的模型、结果、检验与解释，并登记数值来源 |

建议的任务字段如下：

| 字段 | 内容 |
| --- | --- |
| id / stage | 唯一任务 ID 与所属阶段 |
| title / requirement_ids | 可执行动作与对应的题目要求 |
| dependencies | 必须先完成的任务 |
| priority / owner / estimate_minutes | 优先级、责任人和预计投入 |
| outputs / acceptance | 预期产物与可核对的通过标准 |
| status / evidence | 当前状态与真实完成证据 |
| required / blocker / note | 是否必要、阻塞原因、本轮或后续等备注 |

P0 表示阻塞或漏答等优先事项，P1 表示主要质量工作，P2 表示可选改进。预计投入未知时可以为 null，不能虚构已获准的计算时间。

### 6.4 两套状态不能混用

**任务及题目要求状态：**

| 状态 | 含义 | 使用要点 |
| --- | --- | --- |
| TODO | 待做 | 尚未实际完成 |
| DOING | 正在处理 | 不等于已经完成 |
| BLOCKED | 受阻 | 写清缺口及解除条件 |
| DONE | 有依据地完成 | 应有产物、证据和有效上游依赖 |
| SKIPPED | 有理由跳过可选任务 | 必要任务不能用此状态绕过 |
| STALE | 已有成果需要重新核验 | 常见原因是输入、代码或协议变化 |

**阶段与专项检查状态：**

| 状态 | 含义 | 使用要点 |
| --- | --- | --- |
| PASS | 检查实际通过 | 有检查说明、证据与被查输入快照 |
| FAIL | 发现未解决的不通过项 | 应定位原因并安排修复 |
| NOT_RUN | 未执行检查 | 不能解释为通过 |
| BLOCKED | 检查暂时无法开展 | 记录真实原因 |
| NA | 该可选检查确实不适用 | 必须说明理由；必要检查不能直接记 NA |

STALE 是任务状态，不是 record-check 支持的检查状态。证据变化后，先记录实际受影响情况，完成重验后再更新检查结论。

### 6.5 分析完成与题目解答完成

“已经设计预测方案”只能证明分析工作完成，不能证明已经生成预测。

当项目本身使用 analysis 范围时，每条要求可以分别记录：

~~~json
{
  "id": "Q3.a",
  "question": "Q3",
  "description": "生成下一周预测",
  "source": "题面文件第三问",
  "status": "BLOCKED",
  "evidence": [],
  "paper_anchor": "q3-prediction",
  "analysis": {
    "status": "DONE",
    "evidence": ["reports/modeling.md"]
  }
}
~~~

这段结构仅展示状态含义：可以已经设计好方案，同时因缺少未来输入而尚未完成预测。它是要求条目的示例，不是可直接替代整个 state.json 的完整文件。

<a id="writing-gate"></a>
## 7. 论文什么时候可以开始写

**只有计划内实验与必要验证完成，且本轮范围包含论文写作时，才进入 S6。**

写作前逐项检查：

1. 全部题目要求已被完整识别，没有只解决前几问就开始组装全文。
2. 已纳入当前研究计划的基础实验、方法比较和必要检验均已实际完成。
3. G4、G5 有真实且仍然有效的检查依据；仅接手写作时，需核验等效的既有材料。
4. 必要任务没有未处理的阻塞、失效结果或失败；代码写好但未运行不算实验完成。
5. 主要结果、日志、图表来源、单位和场景已核对，结论强度与证据相符。
6. 本轮明确允许写论文；如果本轮停止点是 S5，即使实验完成也先交付结果报告。

无收益或表现较差的结果可以是有效实验结果，应如实说明。实验成功不要求主方案必须优于基线。

明确取消的可选探索需要记录范围调整及理由；必要实验不能为提前写作而改为可选。理论题以应完成的推导、边界验算及适用的数值核验作为对应依据。

### 7.1 实验前可以保存什么

可以保存题意分析、数学推导、假设、文献记录、代码、实验计划、真实日志和结果图。这些属于研究记录，不提前写成论文正文、摘要或“待填结果”的论文稿。

### 7.2 写作过程中发现还要补实验怎么办

记录新问题及影响范围，暂停受影响的结论写作，回到相应实验或验证任务。新的证据确认后，再更新论文数字、图表、论述和检查记录。

更新对应任务与检查，给出下一步建议后停止，不自动重跑或写论文。
~~~

### P19：部分附件缺失

~~~text
使用 $huawei-mathmodel，本轮完成现有材料支持的拆题与方案分析。
缺失附件的名称和影响需要逐项记录，不推测其内容。

继续完成不依赖缺失材料的工作，为受影响问题写明条件化方案、
所需字段、后续接口和解除阻塞的条件。
已有分析可以记录完成，实际预测、求解与验证保持未执行或受阻。
输出最小补充材料清单，更新 plan 与 todo 后停止。
~~~

### P20：数据、参数或代码已经变化

~~~text
使用 $huawei-mathmodel。当前项目有新的数据/参数/代码版本。
请对照旧版本与已有实验记录，分析具体影响范围。

将受影响的完成任务和要求标记为 STALE，保留旧实验与历史结果。
列出需要重跑的实验、需要更新的图表、数字和检查。
仍然有效的部分继续复用，不无条件重跑全部项目。

本轮只完成影响分析和重验计划，不立即运行所有实验。
更新 plan、state 和 todo 后停止。
~~~

### P21：实验失败或求解器报错

~~~text
使用 $huawei-mathmodel，处理当前失败实验。
先读取真实错误日志、输入、配置和相关代码，
区分题意问题、数据问题、数学不可行、实现错误和资源限制。

提出最小修复，并在本轮已允许的运行预算内进行有针对性的检查。
保留失败记录，新尝试使用新的实验 ID。
不能把求解失败、超时或只有局部可行解写成已证明全局最优。
修复成功后记录依据；仍失败时保留问题并给出明确下一步。
处理本次失败后停止，不随意扩大算法搜索。
~~~

### P22：主方案没有优于基线

~~~text
使用 $huawei-mathmodel，分析当前主方案未优于基线的原因。
先确认数据、划分、约束、指标、参数选择和计算预算是否可比。
再判断问题来自实现、优化过程、数据支持还是方法本身。

保留全部真实结果，不挑选有利样本或重复试验中的最好一次。
提出有明确依据的最小后续实验及停止条件；本轮只做分析和计划。
如果证据支持保留基线，请直接说明理由和适用范围。
更新结果报告与 todo 后停止。
~~~

### P23：剩余时间有限，需要收敛工作

~~~text
使用 $huawei-mathmodel，依据我提供的实际截止时间和剩余资源重排任务。

先检查题目覆盖、输入正确性、基础可行性、必要验证和交付缺口。
压缩缺乏明确收益的可选探索，记录取消理由和影响。
保留必要实验、结果核验及交付缓冲，不能靠跳过必要检查声明完成。

本轮输出按优先级排列的剩余 todo、预算与停止点。
未知工时明确写未知，不默认比赛总时长或额外计算资源。
只完成重规划，不立即执行全部新待办。
~~~

### P24：只问状态，不推进任务

~~~text
使用 $huawei-mathmodel，只读取当前项目状态并汇报。
说明当前阶段、已完成任务及证据、受阻任务、失效结果和下一步建议。
区分阶段完成、实验完成、论文完成与完整项目验收。
不要启动实验、修改代码、重写论文或更新完成状态。
~~~

### P25：显式要求连续完成全流程

~~~text
使用 $huawei-mathmodel，在我已提供的材料、资源和授权范围内，
连续推进本项目的完整流程，直到达到可交付条件。

仍需先建立 plan 和 todo，并逐阶段完成相应检查。
阶段之间无需重复确认，但关键输入缺失时应记录阻塞，
不能猜测数据、编造实验、扩大资源权限或省略必要验证。

全部计划内实验和必要验证完成后才开始 Markdown 论文。
持续保存真实进度并汇报重要问题，最终整理验收与交付材料。
不自动执行比赛平台提交。
~~~

这是明确连续执行的入口。它仍受当前环境能力、任务边界和必要输入约束，不代表获得了新的服务器访问权限或额外计算资源。

## 10. 不同题型的指令补充

以下内容可以接在相应阶段指令后使用。题型要求决定检查方法，不应机械套用所有检查。

### P26：优化、调度或路径规划

~~~text
本题属于优化/调度问题，请补充以下要求：
明确目标方向、变量类型、单位、资源共享和时间先后关系。
先验证可行性，再讨论目标改进；独立回代全部原始约束。
记录求解器状态、时间限制、可用上下界及最优性间隙。
连续松弛后取整需要重新检查约束。
没有相应证明或求解证据时，只报告当前最好可行解或局部最优。
多目标之间的权重、优先级和单位换算必须有依据。
~~~

### P27：预测、分类或统计分析

~~~text
本题属于预测/统计问题，请补充以下要求：
按预测时点判断可获得的信息，防止未来信息和对象重复泄漏。
数据划分尊重时间、对象或空间依赖，预处理参数只在训练部分拟合。
调参与最终评价分开，报告实际可支持的验证规模和不确定性。
主指标对应题目目标，同时检查代表性误差和失败情景。
不把相关性或特征重要性直接解释为因果关系。
样本少时先评估信息量与模型复杂度，不仅凭样本数量指定算法。
~~~

### P28：机理、动力学或反问题

~~~text
本题属于机理/动力学问题，请补充以下要求：
写清状态、单位、初始条件、边界条件、参数来源与可辨识性。
检查守恒、非负性、数量级、极限情形和适用的解析特例。
区分模型误差、参数不确定性、数值误差与观测噪声。
按任务精度安排步长或网格收敛检查，容差需要依据。
多个参数组合都能解释观测时，报告可辨识范围和局限，
不虚构唯一参数真值，也不为理论题制造不必要的训练集。
~~~

### P29：综合评价与多指标决策

~~~text
本题属于综合评价问题，请补充以下要求：
先说明评价对象、价值目标和各指标含义，再决定赋权和排序方法。
检查指标方向、尺度、重复信息、缺失处理及权重来源。
说明归一化和降维对结果解释的影响。
比较合理权重与处理规则变化下的排序稳定性。
不能把数据离散程度直接等同业务重要性，
也不能把微小分数差距夸大成确定优势。
~~~

## 11. 一次完整项目如何分轮推进

假设已经选定一题，最终需要完整求解与 Markdown 论文，可以按下面的顺序发起多轮任务。轮数与问题数量按实际项目调整。

| 轮次 | 本轮范围 | 可以复用的指令 | 结束时应拿到什么 |
| --- | --- | --- | --- |
| 第 1 轮 | S0—S3，分析与设计 | 第 2.2 节快速开始指令，或依次使用 P01、P03—P05 | 完整拆题、数据检查、模型方案、实验协议、具体待办 |
| 第 2 轮 | S4，先完成一个关键问题的基线 | P06 或 P15 | 实际运行结果、日志和基础检查 |
| 第 3 轮 | S4，完成其余必要基础实现与联调 | P06 或按任务 ID 使用 P16 | 全问基础结果及依赖正确性检查 |
| 第 4 轮 | S5，方法改进与必要验证 | P07 | 公平对照、误差与必要稳健性等分析 |
| 第 5 轮 | 实验完成盘点 | P08 | 明确的写作前提结论、剩余缺口或已核实结果清单 |
| 第 6 轮 | S6，Markdown 论文 | P09 | 有真实结果依据的全文与支持材料 |
| 第 7 轮 | S7，审查与必要修复 | P10；有问题时再使用 P11 | 审查报告、修复证据和最终检查结论 |
| 第 8 轮 | S8，交付与归档 | P12 | 论文入口、支持文件清单和对应版本快照 |

如果第 4 轮发现模型不成立，就回到 S3 修正后重做受影响部分；如果第 5 轮还有实验缺口，就先补齐再进入第 6 轮。计划中的轮次用于组织工作，不是绕过依赖的固定日程。

### 11.1 每轮结束的汇报格式

可以要求始终按下面的顺序汇报：

~~~text
请按以下顺序汇报本轮工作：
1. 本轮执行了什么，目的是什么。
2. 实际产出与关键结果，给出对应文件入口。
3. 对应任务与阶段检查是否完成，证据是什么。
4. 尚未解决的问题、阻塞及结论局限。
5. 建议的下一阶段、具体任务、输入与停止条件。

只汇报真实完成的工作，不把下一步建议写成已执行内容。
~~~

## 13. 辅助脚本与命令行操作

日常使用可以直接发自然语言指令，由执行者管理这些记录。本节适合希望了解或手动调用脚本的人。

### 13.1 环境与实际能力

- 辅助脚本需要 Python 3.9 或更高版本，仅使用标准库。
- 具体模型使用的库和求解器按题目需要安装，不包含在辅助脚本中。
- 在能够访问完整 skill 目录和项目文件的环境中执行。
- 下列终端示例使用 Bash 语法，适用于相应的 Linux、macOS 或 WSL 环境；其他终端需调整变量与换行语法。
- 先替换路径，再执行命令。不要将本说明中的示例 ID 或检查结论直接当成真实证据。

当前脚本提供 init、sync、record-run、record-check 和 audit；**没有 run-stage、--stage 或 --stop-after 命令。** 分阶段控制由自然语言任务范围、plan 中的执行约定以及执行者遵循 skill 完成，不应把它理解为脚本强制隔离或自动实验调度。

先设置两个项目专用变量：

~~~bash
MM_SKILL_DIR='/替换为/当前安装的完整skill目录'
MM_PROJECT_DIR='/替换为/本次建模项目目录'
~~~

技能目录应包含 SKILL.md 和 scripts。安装位置可能因环境而不同，不把某个个人环境的内部路径写死到比赛代码中。

### 13.2 初始化新项目

下面以明确的训练项目为例。正式比赛使用 competition；不能确定时使用 unknown。

~~~bash
python3 "$MM_SKILL_DIR/scripts/project.py" init \
  --root "$MM_PROJECT_DIR" \
  --title "数学建模训练项目" \
  --mode practice \
  --scope full
~~~

此命令建立 plan.md、todo.md、state.json 和待细化的阶段记录，不会解题、运行实验或生成论文。已存在核心记录的项目应续接，不能重新初始化覆盖。

**mode：**

| 值 | 含义 |
| --- | --- |
| practice | 已明确是训练或练习 |
| competition | 正式比赛任务 |
| unknown | 目前无法确定 |

**scope：**

| 值 | 项目范围 | 初始化包含的阶段 |
| --- | --- | --- |
| full | 完整项目 | S0—S8 |
| analysis | 只交付分析与规划 | S0、S1、S2、S3 |
| coding | 实现、验证和审查 | S0、S1、S2、S3、S4、S5、S7 |
| writing | 核验已有材料后写作与交付 | S0、S1、S6、S7、S8 |
| review | 接收、对照要求与审查 | S0、S1、S7 |

这些值选择的是项目范围，不是本轮停止按钮。最终要完成整题与论文、当前只分析时，可以保持 full 并在 plan 中限定本轮到 S3。

writing 范围不会免除对既有实验的核验；review 范围也不能把有问题的成果变成“已通过”。扩大项目范围时需要补齐相应任务和检查，不能只修改 scope 字符串。

### 13.3 更新待办

先依据真实工作更新 state.json，再执行：

~~~bash
python3 "$MM_SKILL_DIR/scripts/project.py" sync \
  --root "$MM_PROJECT_DIR"
~~~

sync 重新生成 todo.md，不自动修改 plan.md，也不判断模型科学正确性。计划中的路线、停止点和变更原因需要另外维护。

### 13.4 登记一次真实成功运行

**先实际运行，再登记。** 下面假定列出的代码、配置、数据、结果和日志都已经真实存在，且命令与实际执行一致。

~~~bash
python3 "$MM_SKILL_DIR/scripts/project.py" record-run \
  --root "$MM_PROJECT_DIR" \
  --id E001 \
  --status SUCCEEDED \
  --kind execution \
  --command "python3 code/q2_baseline.py" \
  --input code/q2_baseline.py \
  --input configs/q2_baseline.json \
  --input data/clean.csv \
  --output results/e001.json \
  --log results/e001.log
~~~

record-run 保存输入、输出和日志的文件摘要；不会执行 --command 中的模型命令，也不会自动确认你声明的成功状态属实。

--input 和 --output 可以重复。实际使用的辅助代码、配置、数据和上游结果都应纳入记录，不能只登记主脚本。日志应保留实际命令、退出状态和关键设置。

### 13.5 登记失败运行

失败记录同样保留，后续修复使用新 ID。成功与失败不能共用一个 ID 后反复覆盖。

~~~bash
python3 "$MM_SKILL_DIR/scripts/project.py" record-run \
  --root "$MM_PROJECT_DIR" \
  --id E002 \
  --status FAILED \
  --kind execution \
  --command "python3 code/q2_candidate.py" \
  --input code/q2_candidate.py \
  --input data/clean.csv \
  --log results/e002.log
~~~

失败运行可以没有结果输出，但仍需有实际输入与日志。如果本次失败尝试使用了其他配置或依赖文件，也要增加 --input。失败结果可以支持错误分析，不能支持论文中的成功数值结论。

推导型工作可以使用 --kind derivation，命令说明写实际推导或验算方法，输入与日志保存真实依据；不能用这种方式绕过本来需要运行的实验。

### 13.6 登记阶段检查

先实际检查并写报告，再登记结论。下面假定项目中已经定义 G4，且所有列出的文件真实存在。

~~~bash
python3 "$MM_SKILL_DIR/scripts/project.py" record-check \
  --root "$MM_PROJECT_DIR" \
  --id G4 \
  --status PASS \
  --note "已实际完成小实例与原始约束复核，详情见检查报告" \
  --evidence reports/baseline_check.md \
  --input code/q2_baseline.py \
  --input configs/q2_baseline.json \
  --input data/clean.csv \
  --input results/e001.json
~~~

--evidence 是真实审查说明，--input 是被检查的文件。PASS 需要两者的有效快照；原文件变化后需要真实重验，不能只更新摘要让旧结论继续显示为通过。

未执行或受阻时如实记录，例如：

~~~bash
python3 "$MM_SKILL_DIR/scripts/project.py" record-check \
  --root "$MM_PROJECT_DIR" \
  --id G5 \
  --status BLOCKED \
  --note "计划内的独立验证输入尚未提供，当前无法完成该项检查"
~~~

这些 note 也是示例，必须替换为实际情况。检查 ID 必须已在项目中定义；必要检查不能直接设为 NA 来绕过。

### 13.7 进行中审计

阶段执行期间，可以核对记录是否一致，同时允许项目尚未整体完成。

~~~bash
python3 "$MM_SKILL_DIR/scripts/audit.py" \
  --root "$MM_PROJECT_DIR" \
  --output reports/audit.json
~~~

这时 scope_completion=INCOMPLETE 可能是正常状态。应结合本轮任务与相应 G 检查判断当前阶段是否完成，不要求早期阶段就生成完整论文。

### 13.8 完整交付审计

当所选项目范围应全部完成时，执行：

~~~bash
python3 "$MM_SKILL_DIR/scripts/audit.py" \
  --root "$MM_PROJECT_DIR" \
  --require-complete \
  --output reports/audit.json
~~~

发现缺口后按原因修复，不能删除后续必要任务或降低必要性来换取通过。不要把会反复覆盖的 reports/audit.json 用作另一个检查的固定证据，避免形成自引用或失效快照。

### 13.9 冻结已完成交付

完整成果、实际检查、交付说明与相应 G8 均完成后，才进行完整项目的冻结：

~~~bash
python3 "$MM_SKILL_DIR/scripts/audit.py" \
  --root "$MM_PROJECT_DIR" \
  --freeze
~~~

冻结保存当前被跟踪文件的摘要，不会自动上传比赛平台。冻结后的只读核验省略 --output：

~~~bash
python3 "$MM_SKILL_DIR/scripts/audit.py" \
  --root "$MM_PROJECT_DIR" \
  --require-complete
~~~

修改被冻结文件会被检测。需要新修订时，保留旧版和旧快照，另建可编辑的项目版本；新版本不沿用旧版的活动冻结标记，重新核验受影响内容后生成自己的快照。不要覆盖旧快照来掩盖修改。

## 14. 实验、数值与论文的追溯关系

一项论文数值应能沿以下关系核对：具体题目要求、对应任务、真实实验、实验输出中的指标、论文中的引用位置。

### 14.1 结果文件

假设某次真实实验输出了下面的结构。0.92 仅为格式示例。

~~~json
{
  "metrics": {
    "accuracy": {
      "value": 0.92,
      "unit": "1",
      "context": {
        "requirement_id": "Q2.a",
        "split": "test",
        "method": "baseline"
      }
    }
  }
}
~~~

- value 使用真实数值类型，不用数字字符串或布尔值。
- unit 写明单位；无量纲使用字符串 "1"。
- context 说明要求编号、实际场景、数据划分与方法等必要信息。
- 百分比、万元等展示转换应在结果输出中明确完成，不能写论文时静默换算。

### 14.2 论文引用登记

在 state.json 的 claims 数组中登记一次引用，例如：

~~~json
{
  "id": "C001",
  "requirement_id": "Q2.a",
  "experiment_id": "E001",
  "result_file": "results/e001.json",
  "pointer": "/metrics/accuracy",
  "decimals": 4,
  "context": {
    "split": "test",
    "method": "baseline"
  },
  "paper": "paper/paper.md"
}
~~~

pointer 表示 JSON 中指标所在的位置。上例对应 metrics 下的 accuracy 对象。E001 必须是真实成功且仍有效的实验，results/e001.json 必须已登记为它的输出。

### 14.3 Markdown 中的数字

~~~markdown
测试集准确率为 <!-- mm:C001 -->0.9200<!-- /mm:C001 -->。
~~~

普通 Markdown 展示时注释通常不可见，源文件仍保留绑定信息。摘要与正文重复使用同一指标时，应登记两个不同的引用 ID，可以指向同一源指标。

带单位时，单位也放在绑定范围内，例如下面仅展示文本形式：

~~~markdown
成本为 <!-- mm:C002 -->1234.50 元<!-- /mm:C002 -->。
~~~

C002 需要另有对应的实际源指标和登记，不会因出现这段文字就自动成为有效引用。

### 14.4 审计会检查什么

对已登记引用，核对实验是否成功且有效、结果是否属于该实验、文件是否改变、任务与场景是否对应，以及显示数字、精度和单位是否一致。

显示采用十进制 ROUND_HALF_UP 四舍五入，当前支持 0—12 位小数。零、负数与小于 1 的数值同样检查，NaN、Infinity、布尔值和数字字符串不能冒充数值指标。

脚本不能自动发现所有未登记的数字，也不能仅靠字段相符判断场景、模型和引用文献是否真实。S6、S7 仍需阅读实际内容，核对未绑定常数、数学推导与解释。

### 14.5 每个问题如何定位到论文

完整论文中的题目要求应有对应的明确锚点，例如：

~~~markdown
<a id="q2-comparison"></a>
### 第二问的方案比较
~~~

要求条目的 paper_anchor 对应 q2-comparison。多个要求可以定位到同一个相关小节，但仍要逐项确认有实质答案。加上锚点只能解决定位，不能代替科学内容。

### 14.6 文件变更与历史实验

输入、代码、配置、结果或被审查文件变化后，摘要核对会发现不一致。执行者应判断影响范围、标记受影响任务并重新检查；脚本不会自动理解变化的科学影响，也不会自行重跑。

旧实验保留用于追溯。确实不再支撑当前成果的历史实验可以标记 retired=true，同时填写 retirement_reason；仍用于正文或基线比较的实验不能随意退役。退役实验不能继续支撑有效的论文数值引用。

## 15. 审计结果怎么读

### 15.1 主要字段

| 字段 | 常见值 | 含义 |
| --- | --- | --- |
| structural_status | PASS / FAIL | 程序实际检查的结构、记录和文件一致性是否通过 |
| scope_completion | READY / INCOMPLETE / FAIL | 所选项目范围的必要任务、要求与检查是否满足 |
| answer_completion | RECORDED_COMPLETE / INCOMPLETE | 题目要求是否全部被记录为完成；不等于独立科学证明 |
| markdown_delivery_ready | true / false | 对需要论文的范围，是否满足程序检查的 Markdown 交付条件 |
| scientific_status | REQUIRES_DOCUMENTED_REVIEW | 提醒需有真实科学审查；脚本不证明数学正确性 |
| official_submission_status | NOT_ASSESSED | 未核定官方平台提交完成情况 |
| expected_claim_displays | 引用 ID 到显示文本的映射 | 已登记数值按指定精度和单位应如何显示 |
| issues | FAIL / INCOMPLETE / WARN 条目 | 具体问题、未完成事项或需注意内容 |

### 15.2 退出码

| 退出码 | 含义 |
| --- | --- |
| 0 | 实际结构检查通过，并满足当前命令的完整性要求；普通进行中审计仍可能为 INCOMPLETE |
| 1 | 存在检查错误，或命令/记录/文件处理错误 |
| 2 | 使用 --require-complete 要求完整，但仍有未完成事项且没有更优先的硬错误 |

不要只看退出码 0 就说整题完成。普通审计允许一个结构一致、正在推进的项目暂时不完整。

当前实现中，--freeze 在完整条件未满足时会直接拒绝冻结并以退出码 1 返回错误；不要预期它一定返回 2。先运行带 --require-complete 的审计查看具体缺口，再在符合条件后冻结。

### 15.3 常见结果组合

| 情况 | 合理解释 | 下一步 |
| --- | --- | --- |
| S2 完成，但 full 范围为 INCOMPLETE | 当前阶段可完成，后续实验和论文仍未完成 | 保留后续待办，按下一轮范围推进 |
| analysis 为 READY，answer_completion 为 INCOMPLETE | 分析规划已交付，实际求解尚未完成 | 需要求解时扩大工作范围并补齐任务与检查 |
| 数值绑定不一致 | 论文显示值、单位或引用源存在问题 | 对照真实结果修正文稿或错误绑定，不迁就文稿改源数据 |
| 证据已改变 | 当前文件与登记时的版本不一致 | 判断影响并重验，再记录新的有效依据 |
| G7 为 NOT_RUN | 必要最终审查尚未执行 | 完成实际审查，不能只改成 PASS |
| 审查报告完成，但项目 FAIL | 已成功发现项目问题，成果本身尚未通过 | 根据修复清单处理并复验 |

### 15.4 审计覆盖的实际边界

程序能帮助检查任务依赖、必要记录、文件存在性与摘要、已登记的数值引用、答题锚点以及部分 Markdown 分隔符和图片路径。

plan 的路线是否合理、任务证据是否真正回答题意、实验是否公平、公式是否正确、引用是否真实，以及 Markdown 的实际视觉呈现，仍需要对应的内容审查或预览。辅助脚本不提供完整排版渲染，也不承诺自动找出所有科学错误。

## 16. 常见问题与推荐使用习惯

### 16.1 是否必须一口气做到论文

不需要。明确给出本轮范围与停止点即可，例如“只完成 S2，更新记录后停止”。只有明确要求连续全流程时才连续推进。

### 16.2 每个阶段结束都必须再确认吗

本轮已指定 S0—S3 时，可在这个范围内连续完成，无需每阶段重复确认。到 S3 停止后，下一轮由你的新指令决定做什么。阶段交付不需要写成重复的审批请求。

### 16.3 能否只讨论模型、不生成项目文件

可以。简单方法咨询可直接回答；当需要正式规划、执行或续接项目时，再建立和维护计划与状态记录。

### 16.4 可以先写论文，实验数字以后补吗

当前约定是实验及必要验证完成后再开始论文。前期保存分析、推导和文献等研究记录，避免把未经验证的结果提前写成论文结论。

### 16.5 已有结果，是否必须全部重跑

不必。先核对题面、协议、代码、输入版本、日志和结果。仍然有效且证据充分的成果可以复用；不明确或失效的部分才需要补齐或重验。

### 16.6 没有 GPU 能不能用

可以进行题意分析、规划、建模设计以及计算资源允许的实现和验证。具体模型是否需要 GPU 由任务决定。需要外部计算时，可以交付运行包并等待真实结果回传，不能把未运行的实验写成成功。

### 16.7 是否会自动启动多个代理或后台任务

默认不启动多个代理。是否使用额外执行资源取决于当前会话授权和环境能力。skill 不是常驻后台服务，不会仅因写下待办就自动跨会话执行或监控实验。

### 16.8 一道题有五问或更多，是否都能覆盖

可以。要求清单按完整题面动态提取，同时覆盖各问中的比较、解释、画图和输出附件等子要求。不会把固定三问结构当成完整覆盖标准。

### 16.9 没有数值结果的理论题怎么办

使用题设、推导、边界与必要验算作为证据，按实际需要记录 derivation。没有数值引用时仍需检查符号、推导与论证，不能为满足某种固定流程制造数据或实验。

### 16.10 修改 todo 后为什么恢复了

todo.md 由 state.json 生成。需要改变任务状态、依赖或完成证据时，应先更新 state，再运行 sync；plan 中的决策和本轮边界仍需同步维护。

### 16.11 审计显示 PASS，是否就能认为论文正确

先确认看的是什么字段。structural_status=PASS 只表示程序实际检查的记录一致性通过；还需看 scope_completion、相关科学审查报告和论文内容。字段中的 PASS 不能代替真实证据。

### 16.12 冻结后发现错误怎么办

保留旧交付版本与快照，创建新修订，定位受影响范围并修复重验，再生成新的交付快照。不能仅修改旧摘要或删除失败记录来隐藏问题。

### 16.13 Markdown 完成后是否自动完成比赛提交

不会。当前交付范围是 Markdown 论文及支持材料。若后续需要官方格式转换或提交，应另行明确任务，并核实当届规则与实际提交状态。

### 16.14 如何使用这份 README

首次使用时读第 2、3、5、6、7 节，选取合适的阶段指令；实际推进时按第 8—10 节复制并修改；遇到记录、脚本或审计问题时查第 13—15 节。

每次发出指令前，确认材料可访问、本轮范围明确、输出与停止点清楚。每次结束后，检查是否有真实产物、相应证据、更新后的 plan/todo，以及诚实保留的未完成项。

## 17. 论文级绘图规范与 GPT Image 提示词

### 17.1 两类图分别怎样做

本 skill 将“优秀论文的绘图标准”落实为准确、清楚、统一、可复现，而非装饰越多越好。具体规范见 skill 内的 references/figures.md。

| 图的类别 | 默认做法 | 交付物 |
| --- | --- | --- |
| 实验分析图 | 从实际结果用 Python/Matplotlib、R 或既定工具绘制 | 图像、源数据定位、代码、运行方式、图注和检查记录 |
| 论文总体框架图 | 按实际采用的方法梳理模块与依赖，给出 GPT Image 提示词 | 结构说明、节点与连线表、完整提示词、标签清单、图注建议、验收项 |
| 算法流程图 | 梳理实际执行顺序、判断分支、循环与停止条件，给出 GPT Image 提示词 | 同上，另外明确每个分支条件及终止结果 |

默认不调用 GPT Image 生成图片。你可以复制提示词到图像工具使用；以后明确要求生成时，再按环境支持的能力执行。GPT Image 生成的“矢量风格”图片是栅格图，不等于可编辑 SVG。复杂中文或公式可以采用无文字底图加精确标签表，后续叠字。

实验曲线、误差棒、热图数值、排名和显著性证据不能交给图像模型编造。框架图中的真实数据子图也必须由代码生成。生成式图片不能作为数值结果证据。

### 17.2 实验图的默认风格

以下是本项目的起始配置，**不是所有优秀论文、期刊或比赛通用的硬性规格**。以最终 Markdown 阅读效果为准；可以调整，但整篇一致。

| 项目 | 默认要求 |
| --- | --- |
| 背景 | 白底、深色文字，去掉阴影、浮雕、无信息装饰；网格默认关闭，需要读数时用淡灰主网格 |
| 尺寸 | 单幅从 85–90 mm 宽起步，组合图从 170–180 mm 宽起步；在实际 Markdown 显示宽度再次检查 |
| 字体 | 统一无衬线字体；英文 Arial/DejaVu Sans，中文使用实际安装且覆盖所需字符的字体 |
| 字号 | 刻度和图例约 8–10 pt，轴名约 9–11 pt；按最终尺寸检查，密集时拆图而不是无限缩字 |
| 线宽 | 曲线约 1–1.5 pt，轴线约 0.6–0.8 pt，标记约 3–5 pt |
| 离散配色 | 蓝 #0072B2、橙 #E69F00、绿 #009E73、紫 #CC79A7、灰 #7F7F7F 按需选用 |
| 冗余编码 | 颜色结合线型、点形或直接标注；灰度下仍应能区分，不能只靠红绿 |
| 色标 | 连续量优先 viridis/cividis 等顺序色标；有明确中心含义才用发散色标；避免彩虹色 |
| 语义 | 同一模型在全篇保持同色、同名、同线型；主方案适度突出，不能降低基线可见性 |
| 排版 | 图例不挡数据、面板对齐、(a)(b) 标号一致，正文解释放图注而非图内大标题 |
| 导出 | 适合的图保留 SVG，另导出白底 PNG；通常 300 dpi，密集线图可 600 dpi，同时检查真实像素尺寸 |

分辨率必须与最终尺寸一起判断。90 mm 宽、300 dpi 约需 1063 像素宽；给一张小图改写 DPI 标签不能增加细节。把 PNG 放进 SVG 容器也不等于矢量化。

图表没有“统一越高级越好”的类型。例如方法比较可用点区间图，变化趋势用折线，分布用箱线或散点，预测检查用实际-预测散点与残差，敏感性用参数响应曲线，多目标用真实可行解与非支配解集。图型应服务于对应问题和结论。

### 17.3 科学表达比风格更重要

- 误差棒要说清是 SD、SEM、CI 还是其他区间，交代计算方法、样本量及样本单位。单个汇总均值不能凭空补区间。
- 不挑最好一次随机运行，不隐去失败结果，不用未经解释的筛选、平滑和异常值剔除制造优势。
- 方法对比应保持数据划分、约束和评价口径可比；预算不同需明确说明。
- 用柱长表达量值的柱状图原则上从零起；折线和散点按真实分析需要设范围，不能用隐蔽截断夸大差距。
- 对数轴、归一化、缺失值和插值必须说明，缺失不能画成零。
- 图注交代对象、条件、单位、样本、统计定义和面板含义。正文说明图支持什么，也说明不能据此推断什么。
- 无论图多漂亮，都不能自动证明因果、全局最优、收敛或普遍优越性。

### 17.4 分阶段安排与 plan/todo

| 阶段 | 绘图任务 | 完成证据 |
| --- | --- | --- |
| S3 | 决定要回答的图形问题、图型、比较与统计协议 | 制图清单和实验计划；明确请求时可给“拟议方法”提示词 |
| S4/S5 | 根据实际结果生成分析图，核对数字、统计含义和视觉效果 | 绘图代码、实际图像、源结果和逐图检查记录 |
| S6 | 实验和必要验证全部完成后整理论文图表；按最终方法提供框架/流程图提示词 | 合格结果图、图注、提示词包；已生成概念图另有检查记录 |
| S7 | 复核全篇图号、名称、单位、色彩、相对路径、节点和连线 | 实际完成的图形审查记录 |

可以只做某一问的图、只给框架图提示词、只检查图表，而不推进整个项目。S5 的研究图与结果报告允许先做，论文正文仍在全部计划内实验及必要验证完成后开始。

将任务拆成独立可验收动作。例如下列是任务设计示例，**不是已经存在或已完成的任务**：

| 任务 ID | 动作 | 依赖 | 完成标准 |
| --- | --- | --- | --- |
| FIG-Q2-01 | 确定问题二的比较图方案 | 指标、划分和对应要求已明确 | 说明每张图的用途和所需数据 |
| FIG-Q2-02 | 运行制图代码 | 真实结果有效，FIG-Q2-01 完成 | 输出图像及运行记录 |
| FIG-Q2-03 | 核对图与源数据、检查缩印效果 | FIG-Q2-02 完成 | 逐图检查有真实证据 |
| DIAG-01 | 整理最终方法的节点和连线 | 实际方法已确认 | 节点/边表与方法一致 |
| DIAG-02 | 输出 GPT Image 提示词包 | DIAG-01 完成 | 可复制提示词、标签表和核验清单齐全 |
| DIAG-03 | 生成并验收概念图 | 用户要求成图、DIAG-02 完成 | 成图存在且文字/拓扑检查通过 |

只请求提示词时，本轮在 DIAG-02 停止；不要自动创建成图承诺。如果最终论文需要该图片，成图与检查任务仍待完成。提示词文件不能当图片嵌入论文，也不能插入尚不存在的图片路径。

建议按需创建下列项目文件；它们不会由初始化命令自动全部生成：

| 文件 | 内容 |
| --- | --- |
| reports/figure_inventory.md | 图 ID、对应问题、科学目的、图型、实验和源数据、脚本、输出路径 |
| code/plot_style.py 或 configs/figure_style.json | 实际使用的统一样式配置 |
| code/plot_*.py | 实际的制图程序；名称随项目确定 |
| figures/*.png、figures/*.svg | 真正生成的图像 |
| reports/figure_review.md | 数值、统计含义、字体、裁切、色彩、图注和结构检查 |
| prompts/framework_gptimage.md | 论文方法框架图提示词包 |
| prompts/workflow_gptimage.md | 算法流程图提示词包 |

这些是工作约定，skill 没有预装一个通用自动画图引擎。现有 audit.py 不会自动判断图是否美观、中文是否写错、箭头是否正确或统计方法是否合理。

### 17.5 GPT Image 提示词必须包含什么

每个提示词包应有以下内容：

1. **用途和事实依据**：解释哪一部分实际方法，以及依据的建模报告/实现。
2. **节点表**：节点 ID、精确名称、输入输出、所属分组；默认图中文字用中文。
3. **连线表**：起点、终点、方向、含义；流程图补充分支、循环和停止条件。
4. **布局**：阅读顺序、分组、画幅比例、对齐与间距。复杂结构拆成概览和局部图。
5. **视觉要求**：白底、扁平、克制配色、深色文字、统一线宽与箭头、足够留白。
6. **限制**：不添加模块、反馈边、指标、图表、徽标或未经验证的效果；不改变科学逻辑。
7. **验收清单**：逐字核对标签、逐条核对边与分支、缩印检查。
8. **修订提示词**：定位错误并给出正确内容；必要时改为无文字底图和标签位置表。

提示词可以用英文写布局要求、用中文明确图内标签。语言选择不影响“精确标签不可随意改写”的要求。图像工具不保证每个汉字、公式或精确字号都正确，成图必须实际检查。

### 17.6 完整提示词示例如何使用

skill 的 references/figures.md 附有两个完整示例：

- **数据检查—参数估计—优化—可行性检验框架**：给出六个节点、五条明确连线、分组颜色和版式。
- **带收敛判断与迭代上限的算法流程**：区分“输出收敛解”和“输出当前可行解（未收敛）”，明确判断分支和回边。

它们是教学示例，不代表某道真实赛题的方法。实际调用 P32/P33 时，skill 应生成与你的题目和代码一致的完整提示词，不能只返回“画一个优秀论文风格的框架图”或留下一串未填的模块占位符。

下面给出可以直接复制到 GPT Image 的**教学示例**，适用于真实方法确实符合所列结构时。实际项目应先核对结构，再使用：

~~~text
Create a clean academic method framework diagram on a white background.
Use a flat vector-like appearance with a landscape 3:2 composition.
Arrange two aligned rows of three modules:
row 1 left to right A, B, C; row 2 right to left D, E, F.
Render only these exact Chinese labels; do not print the reference IDs:
A “原始数据”, B “数据检查”, C “参数估计”,
D “优化求解”, E “可行性检验”, F “方案输出”.
Draw exactly A->B, B->C, C->D, D->E, E->F.
Label E->F with “通过”. This is a high-level framework, not a complete
failure-handling flowchart. Do not imply that failed solutions are accepted.
Use pale blue for A–B, pale green for C–D and pale orange for E–F.
Use dark readable text, consistent thin borders and modest arrowheads.
Align all boxes, preserve generous spacing and avoid lines crossing text.
Keep the diagram readable at approximately 180 mm display width.
No extra nodes, feedback arrows, equations, numerical results or charts.
No logos, decorative icons, 3D, glow, shadows, textures or gradients.
Do not place a title or caption inside the image.
Preserve every Chinese label exactly; do not change the scientific structure.
~~~

此例仍需检查全部标签和 A→B→C→D→E→F 五条边。成图外观为矢量风格，不保证得到真正矢量文件。如果真实模型存在失败处理、分支或反馈，应根据实现重写，不能直接套用此结构。
