## plan.md 必须表达的内容

用中文写清以下内容，不停留在通用阶段清单：

1. 任务目标：比赛/年份/题号、项目总范围、本轮阶段或任务范围、用户明确要求、停止点与本轮交付。
2. 当前状态：已经核实的成果、最新版本、未验证内容、剩余时间。
3. 材料与规则：题面和附件来源、更正版本、官方规则链接和核对时间；未知项明确写未知。
4. 总体路线：各问题如何连接，先解决哪个关键瓶颈，基线、主方案和备选为何这样选。
5. 阶段表：S0—S8 的输入、行动、产物、通过标准、预算、状态、失败回退。
6. 里程碑：首次有效结果、全问基础覆盖、结果定稿、文稿定稿、交付缓冲；用已知实际截止时间或相对剩余时间。
7. 资源安排：执行者、已获准CPU/GPU、语言、求解器、单次运行上限、存储位置。
8. 实验与选择协议：主指标、对照条件、划分、调参范围、随机性处理、结果选择方法。
9. 决策与变更记录：时间、问题、备选、选择、理由、受影响文件/任务、需要重验的结论。
10. 阻塞与恢复：缺什么、阻塞哪些要求、可继续哪些任务、如何解除、何时转用备选。

已定用户偏好直接沿用。排版引擎不属于本 skill 的规划问题。

## 本轮范围与阶段停止

在plan开头写明本轮执行卡：执行阶段、关联题号/任务ID、所需上游证据、预期产出、通过条件、停止位置、论文写作是否开放。未开放S6时明确“实验记录可以更新，论文尚不开始”。这属于执行约定，不需要增加脚本命令。

| 用户请求 | 本轮执行边界 |
| --- | --- |
| “先做S0—S3，设计好方案后停” | 完成接收、拆题、数据检查与模型/验证设计，保留实验任务待做 |
| “只做S4” | 核验已完成的上游，完成基础实现及G4，不扩展到S5或论文 |
| “只跑问题二的基线” | 执行关联基线任务与其必要检查，不把问题二其他任务标完成 |
| “继续” | 当前阶段未通过则继续处理；通过后转入下一个可执行阶段并在其结束处停止 |
| “实验全部完成后写论文” | 核验写作前提；符合才进入S6，缺实验则列出缺口，不生成论文占位稿 |
| “连续完成整个项目” | 已明确授权连续推进，但仍须逐阶段检查并遵守实验先于写作 |

todo保留全部已知任务；在任务note标明“本轮执行”或“后续阶段”。其自动生成的“下一步”只表示依赖已满足，不代表所有列出的任务都属于本轮授权。只选择执行卡内的任务。

阶段结束时提供：本轮目标与实际动作、产出及关键结果、对应G检查结论、未决问题、建议下一阶段。不要把阶段末尾写成重复审批请求。用户下一次发来“继续”即按上述规则续接。

项目scope=full时，早期阶段的全项目审计显示INCOMPLETE是正常状态。按本轮任务与相应G判断阶段完成；不要为让完整性检查通过而删除后续任务、改小scope或提前标DONE。--require-complete用于所选项目范围的完整交付，不是每一小阶段都必须达到的条件。

## todo.md 的任务粒度

以 state.json 为结构化任务来源，由 project.py sync 生成 todo.md。plan.md 是人工维护的解释性计划，不被 sync 覆盖。

每行包含：

| 字段 | 要求 |
| --- | --- |
| id | 唯一且稳定，如 S2.T03；不要在续接时重新编号 |
| stage | S0—S8 |
| title | 一个可执行且可判定完成的动作 |
| requirement_ids | 关联具体要求，如 Q2.a；纯组织工作可为空 |
| dependencies | 任务ID；有数据依赖的工作不能提前标完成 |
| priority | P0：阻塞或漏答；P1：主要质量；P2：可选改进 |
| estimate_minutes | 单次工作预算，可为null；未知不编造 |
| owner | 实际执行者或责任人，不虚构协作者 |
| outputs | 预期文件，未产生时可列计划路径 |
| acceptance | 可核实完成标准，不写“效果很好” |
| status | TODO/DOING/BLOCKED/DONE/SKIPPED/STALE |
| evidence | 已产生的证据路径；DONE时至少一项 |
| required | 是否为当前范围必要任务 |
| blocker | BLOCKED时写具体缺口 |
| note | 跳过理由、结果简述、版本变化或下一动作 |

初始化的每阶段任务是待细化骨架；读题后拆成实际任务。不要把骨架全部勾选当作解题完成。

坏任务：“完成问题二”。
好任务：“用问题一估计参数求解场景A，导出方案，并独立回代全部容量与整数约束”。
好任务：“检查第五问中两种场景的比较表是否都已生成，且正文说明差异来源”。

## 要求覆盖

在 requirements 数组登记全部要求：id、question、description、source、status、evidence、paper_anchor。顶层问题数量按题目动态确定；每个子要求都要有完成证据。

status始终表示该题目要求本身的解答状态。用户只要求分析规划时，不把“预测方案已设计”记作“预测已完成”。在scope=analysis中，另为每条要求增加analysis字段，如 {"status":"DONE","evidence":["reports/modeling.md"]}，表示本轮分析已完成；原status仍按实际保留TODO或BLOCKED。分析证据需要说明方法、验证协议、缺口及后续动作，并关联一个当前范围内完成的任务。尚未完成必要分析时analysis.status保留TODO或BLOCKED。

G2按当前范围判断：分析范围可以在现有数据已真实检查、缺失材料及影响已明确、方案已条件化后通过；涉及缺失材料的实际预测/求解仍保留BLOCKED。完整求解不能沿用分析范围的通过结论冒充数据已齐备。扩大scope时补齐必要阶段、任务和检查，并重新核验受影响的G条件。

source 写原文文件与页码/段落、题面原句或准确定位。保存用户直接提供的题面文本时注明来源。

对于无独立小问编号的多动作要求，使用 Q1.a、Q1.b 等内部编号，不修改题意。分析、比较、解释、画图、输出附件分别覆盖。论文小节可以合并，任务覆盖不能合并丢失。

完整论文要求 DONE 的要求都能定位到 paper/paper.md 内的显式锚点：

~~~markdown
<a id="q2-comparison"></a>
### 两种场景的比较
~~~

在 state 中记录 paper_anchor 为 q2-comparison。不同要求可以共享同一个相关锚点，但必须各有证据。

## 每次续接

依次读取 plan、state、todo、当前阶段相关报告，再检查关键证据文件是否存在及版本是否一致。不要依赖上一轮口头“完成”。

新数据、官方更正、参数修正、代码修改或评价协议变化后：
1. 在 plan 记录原因、版本及影响范围。
2. 给受影响的任务/要求标 STALE；依赖这些结果的下游工作也标 STALE。
3. 使用新的实验ID重新运行，保留旧实验以供追溯。
4. 重建相关图表与数字绑定，重新记录受影响检查。
5. 更新 todo，并告知用户变化和下一步。

历史实验可以 retired=true，必须填写 retirement_reason；历史记录保留。已退役实验不得继续支撑论文或最终结论。仅与当前交付无关的旧实验才退役，不靠退役掩盖失败结果。

## 时间与停止

根据实际剩余时间安排预算，不固化比赛时长。未知截止时间时询问一次或按明确的相对预算工作，同时记录不确定性。

优先顺序：输入正确和任务覆盖 → 可行基线 → 主要模型与证据 → 论文一致性 → 可选改进。

给每个探索任务设置预算与转向条件，如首次可行解期限、允许的搜索轮次和备选路线。失败后先定位题意、数据、数学或实现原因；不要反复无依据增加计算量。

接近截止时停止低收益扩展，保留必要的结果检查与交付缓冲。时间不足时如实降低研究范围/结论强度，不能省掉必要检查后宣布通过。

## 与用户交流

进度更新固定说明：本步行动及目的、实际结果、仍存在的问题、下一步和预计投入。给用户解释术语；代码和运行命令可用英文。

不重复询问已定事项。本轮范围内的阶段转换无需反复确认，达到指定停止点后交付阶段成果并结束；下一阶段留作后续任务。不把“等你确认再继续”作为常规结束语。对确实阻塞的题意只问最关键的问题，并继续完成本轮范围内不受影响的工作。
